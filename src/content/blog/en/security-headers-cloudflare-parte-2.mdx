In the first part of this article, I dealt with the most visible side of the problem: security headers on a static site hosted on GitHub Pages, with Cloudflare coming in as an edge layer to apply what GitHub Pages does not let you configure directly.

But security does not end at the HTTP header. Once the edge was protected, I still had to look inside the project: old dependencies, removed APIs, the build breaking after an upgrade and small code patterns that could turn into security regressions in the future.

This part 2 is exactly that stage: turning the `npm audit` scare into a controlled migration to the latest Astro.

## Context: analyzing the security of a static site

Being more used to Rails applications, my first ideas came from a traditional white-box analysis, using tools common in Ruby/Rails projects, such as Brakeman and RSpec specs focused on route authorization.

But this blog is not Rails. It is a static Astro project. There is no ActiveRecord, no controller, no authentication and no RESTful API in the repository. That is when the research began:

| In a Rails app                  | In this Astro project                               |
| ------------------------------- | --------------------------------------------------- |
| Brakeman                        | `npm audit`, ESLint, TypeScript and white-box tests |
| SQL injection in ActiveRecord   | Vulnerable dependencies and unsafe HTML             |
| Authentication bypass on routes | Regressions in links, CSP, scripts and rendering    |
| Authorization specs             | Security specs on the source code                   |

## First diagnosis: npm audit

I started with the simplest command:

```bash
npm audit --audit-level=moderate
```

Why use this command?

Because it queries npm’s advisory database and cross-references it with the actual tree in `package-lock.json`. `--audit-level=moderate` makes the command fail when there is a moderate or worse vulnerability, which is useful for CI.

The initial result was:

```text
28 vulnerabilities (2 low, 8 moderate, 18 high)
```

Most of it came from transitive dependencies of the old stack: `astro`, `esbuild`, `rollup`, `sharp`, `postcss`, `prismjs`, `yaml`, `devalue` and the like.

![Terminal-style screenshot showing how npm audit evolved: first 28 vulnerabilities, then the migration and finally zero vulnerabilities](/images/security-part2-audit-migration.en.svg)

In the first part, I mentioned that `npm audit fix` tried to bump Astro’s major version and that this should not be treated as an automatic fix. This time the update was intentional: I treated it as a framework migration, not as "just updating a package".

## The dangerous command: npm audit fix --force

The command I used was:

```bash
npm audit fix --force
```

Why use it?

Because the audit listed available fixes, but several of them required an upgrade. `--force` lets npm cross SemVer boundaries and install potentially incompatible versions.

Why is this dangerous?

Because npm itself warns you:

```text
npm warn using --force Recommended protections disabled.
npm warn audit Updating astro to 7.1.3, which is a SemVer major change.
```

That warning is the most important part of the command. It does not mean "done, secure". It means: "you have now accepted breaking compatibility and you need to actually migrate the project".

After `--force`, the audit dropped a lot, but some vulnerabilities related to `vite` and `esbuild` remained:

```text
2 vulnerabilities (1 moderate, 1 high)
```

At that point, the upgrade had turned into a can of worms: `astro@7.1.3` was installed, but some old integrations still pulled in vulnerable or incompatible versions.

## Confirming the latest Astro version

Before moving on, I checked the latest version published on npm:

```bash
npm view astro version
```

Result:

```text
7.1.3
```

In other words: yes, the project was migrated to the latest Astro version available at the time.

Why does this matter for security?

An old framework piles up two kinds of risk:

- known vulnerabilities in direct or transitive dependencies;
- old, deprecated APIs that keep working until the day they disappear.

In this project, both happened: the previous Astro version depended on vulnerable packages in the dependency chain, and the migration to Astro 7 exposed the use of APIs that had already been discontinued.

## Aligning the dependency tree

After `audit fix --force`, I checked the tree:

```bash
npm ls astro @astrojs/mdx @astrojs/react @astrojs/tailwind vite esbuild
```

This command is useful because the problem is not always in the direct package. Sometimes the root looks updated, but a peer dependency or transitive package still pins a vulnerable version.

The main conflict was this one:

```text
@astrojs/tailwind@5.1.5
peer astro "^3.0.0 || ^4.0.0 || ^5.0.0"
```

Since the project was now on `astro@7.1.3`, this old integration no longer made sense. Astro’s own documentation marks `@astrojs/tailwind` as deprecated and recommends the current Tailwind path through the styles pipeline.

I removed the integration:

```bash
npm uninstall @astrojs/tailwind
```

And updated the packages that needed to follow the upgrade:

```bash
npm install @astrojs/react@^6.0.1 @astrojs/check@^0.9.9 autoprefixer@^10.5.4
npm install --save-dev vite@^8.1.5
```

Adding `vite@8.1.5` directly to the project resolved the peer that was still making npm keep an old copy of Vite at the top level. After that, the audit came back clean:

```bash
npm audit --audit-level=moderate
```

```text
found 0 vulnerabilities
```

## Tailwind without @astrojs/tailwind

By removing the old integration, I had to make explicit what it did behind the scenes: plug Tailwind into the CSS pipeline.

I created an entry CSS file:

```css
@tailwind base;
@tailwind components;
@tailwind utilities;
```

And imported it in the base layout:

```astro
import '@/styling/tailwind.css'
```

I also added a `postcss.config.cjs`:

```js
module.exports = {
  plugins: {
    tailwindcss: {},
    autoprefixer: {},
  },
}
```

Why was this done?

Because I preferred to keep Tailwind 3, which was already the project’s stack, instead of mixing two big migrations at once: Astro 7 and Tailwind 4. Security is also about reducing variables. First stabilize the framework, then migrate the design system if it makes sense.

## Real breaking changes in Astro 7

After aligning the packages, I ran:

```bash
npm run build
```

And the first real breakage showed up:

```text
[MISSING_EXPORT] "ViewTransitions" is not exported by "\0astro:transitions".
```

The fix was to replace:

```astro
import {ViewTransitions} from 'astro:transitions'

<ViewTransitions />
```

with:

```astro
import {ClientRouter} from 'astro:transitions'

<ClientRouter />
```

According to Astro’s official upgrade guide, `ViewTransitions` was renamed to `ClientRouter`. The idea is to make it clearer that this component enables client-side routing, not just the browser’s native view transitions API.

Another breaking change was `Astro.glob`. In the new Astro, it was removed from the API. The replacement was to centralize post loading in `src/utils/blog.ts` using `import.meta.glob`:

```ts
const blogPostModules = import.meta.glob<BlogPostModule>(
  '/src/content/blog/*.mdx',
  {
    eager: true,
  },
)

export const getBlogPosts = () => Object.values(blogPostModules)
```

Why centralize?

Because `Astro.glob` used to be in several places: the menu, search, the blog page and the dynamic post page. If the way content is loaded changes again, there is now one main place to change it.

## TypeScript, ESLint and the hidden warning

After the upgrade, TypeScript also had to keep up with Astro’s new tsconfig:

```bash
npm install typescript@^6.0.3
```

With TypeScript 6, ESLint started warning that `@typescript-eslint` was out of date:

```text
WARNING: You are currently running a version of TypeScript which is not officially supported by @typescript-eslint/typescript-estree.
```

This kind of warning should not be ignored. Broken lint or an outdated parser means part of the analysis is running outside its supported range.

I updated:

```bash
npm install --save-dev @typescript-eslint/eslint-plugin@^8.65.0 @typescript-eslint/parser@^8.65.0
```

Then I ran:

```bash
npm run lint
```

Result:

```text
> eslint .
```

No errors. No incompatible TypeScript warning.

I also had to rewrite a piece of `ThemeSwitcher.astro`. The build accepted TypeScript inside the `<script>`, but the ESLint parser stumbled on some generic calls split across multiple lines. The solution was to keep the typing but break the chains into local variables:

```ts
const switchers = document.querySelectorAll<HTMLElement>('.theme-switcher')

switchers.forEach((root) => {
  if (root.dataset.bound === 'true') return
  root.dataset.bound = 'true'
})
```

That made the code more readable and compatible with both tools: `astro check` and ESLint.

## Security tests on the code

The most important part for me was not leaving this as a one-off cleanup. I created a test script using `node:test`, without adding a new framework:

```bash
npm run security:test
```

The test walks through the files in `src` and `public` and looks for patterns I do not want coming back into the project.

The combined command became:

```bash
npm run security
```

It runs:

```bash
npm run typecheck
npm run security:test
npm run security:audit
```

Final result:

```text
# tests 6
# pass 6

found 0 vulnerabilities
```

![Visual matrix listing the automated tests covered: safe external links, raw HTML blocking, dynamic execution blocking, inline handler blocking, CSP and Referrer-Policy](/images/security-part2-test-coverage.en.svg)

Today the site is covered by these automated tests:

| Test                                                                          | What it prevents                                                   |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `target="_blank"` requires `rel="noopener noreferrer"`                        | Tabnabbing and unwanted access through `window.opener`             |
| Blocking `set:html`, `is:raw`, `dangerouslySetInnerHTML` and `innerHTML=`     | Regressions with raw HTML and XSS risk                             |
| Blocking `eval()` and `new Function()`                                        | Dynamic code execution                                             |
| Blocking inline handlers in markup, such as `onerror=`                        | A common XSS surface and a weaker CSP                              |
| Checking the CSP in `astro.config.mjs` and Referrer-Policy in the base layout | Accidental removal of the policies from the `<head>` and the build |
| `npm audit --audit-level=moderate`                                            | Dependencies with moderate or worse vulnerabilities                |
| `tsc --noEmit`                                                                | Type incompatibilities after upgrades                              |

On top of that, the final build ensures the static pages are still generated correctly:

```bash
npm run build
```

- 0 errors

- 0 hints

## Why migrate to the latest Astro?

Migrating a framework is work. In this case, APIs broke, and Tailwind, TypeScript, ESLint and post loading all needed changes. So the honest question is: why do it?

Because staying on an old version creates invisible debt. The site keeps loading, but the foundation slowly loses support in the surrounding tools. The audit starts flagging vulnerabilities in transitive packages. Integrations get deprecated. Old APIs keep working for compatibility until they are removed.

In my case, the migration brought three clear wins:

- the dependency tree went from vulnerable to `found 0 vulnerabilities`;
- old APIs were replaced with current ones during the migration (`ClientRouter` and `import.meta.glob`);
- the project gained security tests that run locally and can go into CI.

In other words, the migration was not just "having a new number in package.json". It was a real reduction in operational risk.

## Next steps

This round covered a lot, but there are still good things to test in a third stage.

1. Validate the headers directly in production after the deploy.

```bash
curl -I https://www.marcopicanco.com
```

The goal is to confirm that Cloudflare keeps applying `X-Frame-Options`, `X-Content-Type-Options`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` and HSTS.

2. Run an external header scanner.

Tools such as Security Headers, Mozilla Observatory or OWASP ZAP in passive mode help check the real behavior in the browser and at the edge.

3. Automate it in CI.

Ideally, create a workflow that runs:

```bash
npm ci
npm run lint
npm run security
npm run build
```

That way, a dependency vulnerability, a CSP regression or a broken build fails before the deploy.

4. Review the CSP calmly.

At that point, `'unsafe-inline'` was still in `script-src` and `style-src` because of the runtime and the inline styles generated on the static site. Part 3 tackled this with Astro 7’s native CSP, hashes generated at build time and the `npm run security:csp` command. `script-src` no longer depends on `unsafe-inline`; the remaining exception is narrower, in `style-src-attr`.

5. Consider Content Collections.

`import.meta.glob` solved the migration, but the more structured path for content in Astro is Content Collections. It would help validate the frontmatter, types and structure of the posts more robustly.

6. Run a non-destructive DAST sweep.

After the deploy, it is worth testing known routes, sensitive files, caching, HTTP -> HTTPS redirects, headers by asset type and the behavior of `www` vs. the root domain.

## Conclusion

Part 1 closed the door at the edge: headers, DNS and Cloudflare.

Part 2 secured an important part of the house from the inside: dependencies, framework, build and automated tests.

The main point is this: security on a static site is not about configuring a header once and forgetting about it. It is about keeping the dependency chain up to date, understanding the impact of major upgrades, automating regression checks and validating in production. The site may be simple, but the discipline has to be the same.
