After running into a flood of news about `cyber security`, I decided to test my own site, which is quite simple, by the way: a static application hosted on GitHub Pages. I ran a security scanner and the result came back full of warnings: `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy` were missing. An `Access-Control-Allow-Origin: *` also showed up.

Before adding headers left and right, I had to understand a limitation that many people hit when hosting a static site (SSG): **GitHub Pages does not let you set custom HTTP headers**. There is no `_headers` file like on Netlify, and no server control. What GitHub serves is what the visitor gets. So now what?

That split the problem into two parts.

## Part one: what can be fixed in the code alone?

After some research, I found that `Content-Security-Policy` and `Referrer-Policy` have an equivalent through `<meta>` in the HTML `<head>`, so they can be applied straight in the site build.

I added this to the root layout (`Base.astro`):

```html
<meta name="referrer" content="strict-origin-when-cross-origin" />
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'"
/>
```

Two important caveats:

- A CSP delivered through `<meta>` **ignores the `frame-ancestors` directive**, which is precisely the one that protects against clickjacking. It only works as a real HTTP header.
- The Astro compiler renders the HTML with inline styles, while its hydration runtime injects `<style>` for interactivity. Without a server there is no way to generate a nonce per request, so I had to allow `'unsafe-inline'` in both, otherwise search, the theme switcher and the mobile menu break.

Update after the migration: in part 3, this decision was revisited. `script-src 'unsafe-inline'` was removed and replaced with hashes generated by Astro 7. The remaining exception is narrower: `style-src-attr 'unsafe-inline'`, used by the `style=""` attributes of the code blocks.

Before wrapping up, I ran some extra tests: I built the production version, inspected the interactions through the CDP protocol in headless Chrome and watched the console during critical flows (search, theme switching, mobile menu and post navigation). The first round revealed a real block: the blog posts load fonts from Google Fonts through `@import`, and my initial CSP did not allow that domain. Since I had taken this free Astro theme and customized it bit by bit, I had not even noticed that small detail, so I adjusted `style-src` and `font-src` to include `fonts.googleapis.com`/`fonts.gstatic.com` and the error went away. Later on I would realize I had to update the theme, but that comes further down the road.

## Part two: what can only be fixed with a proxy in front?

`X-Frame-Options`, `X-Content-Type-Options` and `Permissions-Policy` **only exist as HTTP headers**: there is no equivalent meta tag that browsers honor. Since GitHub Pages does not expose them, the solution was to put the domain behind **Cloudflare** (free plan, of course!) and use a **Transform Rule → Response Header Transform Rule** to inject the headers into the response before it reaches the visitor:

| Header                         | Value                                                          |
| ------------------------------ | -------------------------------------------------------------- |
| `X-Frame-Options`              | `SAMEORIGIN`                                                   |
| `X-Content-Type-Options`       | `nosniff`                                                      |
| `Permissions-Policy`           | `geolocation=(), microphone=(), camera=(), payment=(), usb=()` |
| `Access-Control-Allow-Origin`  | `https://www.marcopicanco.com`                                 |
| `Cross-Origin-Opener-Policy`   | `same-origin`                                                  |
| `Cross-Origin-Resource-Policy` | `same-origin`                                                  |

![Diagram showing that CSP and Referrer-Policy are handled through a meta tag in the HTML, while X-Frame-Options, X-Content-Type-Options, Permissions-Policy and CORS only exist as HTTP headers and are therefore handled at the edge, by Cloudflare](/images/security-headers-scope.en.svg)

With Cloudflare in front, I also took the chance to strengthen TLS: `Always Use HTTPS`, `Automatic HTTPS Rewrites` and HSTS. With HSTS I went slowly: before enabling `includeSubDomains`, I checked with `dig`/`host` whether any subdomain still lacked HTTPS, because this setting is **hard to undo** (the browser keeps the policy for months) and preloading on `hstspreload.org` is practically a one-way street. So, BE VERY CAREFUL.

## The trap: configuring Cloudflare does not mean you are protected

This is where a very important detail lives. After creating the Transform Rule with all the headers, I tested the site in production to confirm, and the response headers were **identical to the ones in the original report**: `server: GitHub.com`, `via: 1.1 varnish`, `x-fastly-request-id`, no `cf-ray` at all, none of the configured headers. Nothing had changed.

The reason: I had set up the rule in my Cloudflare account, but the **domain had never been delegated to Cloudflare**. The nameservers were still the registrar’s defaults (Google Domains, now Squarespace Domains), pointing straight to GitHub Pages. In other words, real visitor traffic never came anywhere near Cloudflare: the rule existed, but it was doing nothing. I ran:

```bash
dig +short NS marcopicanco.com
```

And confirmed it: Squarespace nameservers, not Cloudflare. Zero practical effect from everything I had configured up to that point.

The fix was to replace the nameservers in the registrar’s dashboard (Squarespace → **Domain nameservers**) with the two that Cloudflare assigned when I added the domain (something like `xxxx.ns.cloudflare.com` and `yyyy.ns.cloudflare.com`). After saving, Squarespace warned that the change could take up to 48 hours to propagate. In practice, `dig +short NS marcopicanco.com` already showed the new nameservers within a few minutes.

Even with DNS propagated, there was one more step: hitting a Cloudflare IP directly for this domain returned a TLS handshake error (`SSL routines::sslv3 alert handshake failure`). Cloudflare detects the nameserver change periodically, not instantly, and only then issues the SSL certificate (Universal SSL) for the domain. Until that certificate is ready, the HTTPS connection does not even complete. So the real waiting sequence was: DNS propagation → Cloudflare detecting the zone → certificate issuance → only then did the headers take effect.

![Diagram comparing the network flow before and after: before, the visitor went straight to GitHub Pages because the nameservers still belonged to the registrar and Cloudflare was off the path; after, with the nameservers pointing to Cloudflare, traffic goes through the edge and receives the security headers before reaching GitHub Pages](/images/security-dns-before-after.en.svg)

The lesson: **after configuring any edge protection (Cloudflare, WAF, CDN), always validate directly against the production URL**. Headers configured in a dashboard are worth nothing until traffic actually flows through there. A "ready" rule that is never applied is worse than having no rule at all.

## Tying up other loose ends

Since this is a personal site I use for learning, I quickly ran a light, non-destructive sweep on it: I tried requesting `.git/config`, `.env`, `package.json`, `astro.config.mjs` and other files that are commonly left exposed by mistake. All returned 404, as expected (only `dist/` is published). Valid TLS certificate, TLS 1.2/1.3 responding normally.

Two things that did not exist and are good practice for any site, not directly related to the original report:

- **`robots.txt`**: fixed the route error (404) on GitHub Pages by adding the file, configured to allow indexing of the whole site.
- **`security.txt`** ([RFC 9116](https://www.rfc-editor.org/rfc/rfc9116)): the standard file (`/.well-known/security.txt`) that tells anyone who finds a vulnerability how to report it, without having to hunt for my contact details. I pointed it to my LinkedIn.

## Dependencies and automation

I ran `npm audit` and it found vulnerabilities in Astro’s transitive packages (rollup, sharp, prismjs, yaml). I tried `npm audit fix`, and it "fixed" them by jumping Astro from v4 to v7 in one go, which broke the build (`ViewTransitions` no longer exists in the new API). Reverted on the spot. A major version upgrade is not a security fix, it is a migration, and I will do it calmly, at another time, testing each part. (Yes, it will happen, in part 2 of this article.)

What is now automated so I do not forget about this again: a `.github/dependabot.yml` with weekly checks for `npm` and `github-actions`, plus Dependabot security alerts enabled on the repository. That way, the next vulnerability brings a notice (or a PR) instead of me finding out only when I run the scanner again.

## Summary

| Item                              | Where it was fixed                   |
| --------------------------------- | ------------------------------------ |
| Content-Security-Policy           | `<meta>` in the HTML                 |
| Referrer-Policy                   | `<meta>` in the HTML                 |
| X-Frame-Options                   | Cloudflare (Transform Rule)          |
| X-Content-Type-Options            | Cloudflare (Transform Rule)          |
| Permissions-Policy                | Cloudflare (Transform Rule)          |
| Loose Access-Control-Allow-Origin | Cloudflare (Transform Rule)          |
| HSTS                              | Cloudflare (Edge Certificates)       |
| DNS delegation to Cloudflare      | Nameservers changed at the registrar |
| robots.txt / security.txt         | New files in `public/`               |

A static site on GitHub Pages is great for its zero cost and simplicity, but it is worth knowing where what the code can fix on its own ends and where what needs a network layer in front begins. And, more importantly, **test directly against the production URL** before calling it done. 🔒
