In the first three parts, I went from a header report with no configuration at all to something more solid and secure: Cloudflare in front of GitHub Pages, a hash-based CSP, HSTS, security headers applied at the edge, updated dependencies and automated checks. Everything was going really well.

But security NEVER ends when the first scanner turns `green`. After the initial fixes, I ran new checks with **Cloudflare Security Insights**, the **Pentest-Tools Website Vulnerability Scanner Light**, **Probely/Snyk** and manual tests with `curl` (nothing beats the terminal for this kind of analysis).

This part 4 closes the initial stage: fix what was still basic tuning, separate false positives from real risk and prepare the ground to explore other vulnerabilities more calmly. After all, `cybersecurity` is new to me, and I am using my own site as a field of study. Getting to know and study new topics has been a pleasure.

## What did the scanners still flag?

Even after the header fixes, Cloudflare Security Insights still listed a few items:

| Insight                       | Severity | Practical reading                                             |
| ----------------------------- | -------- | ------------------------------------------------------------- |
| `Security.txt not configured` | Low      | real: the URL still returned `404` in production              |
| `Domains without HSTS`        | Moderate | already fixed in production; the scan was lagging behind      |
| `Bot Fight Mode not enabled`  | Moderate | recommended adjustment in Cloudflare                          |
| `Dangling A Record detected`  | Moderate | likely false positive for the official GitHub Pages A records |
| `Review unwanted AI crawlers` | Low      | optional: enable AI Labyrinth if it makes sense               |

Pentest-Tools gave a similar summary, with an overall **Low** risk:

| Finding                                   | Interpretation                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| Unsafe CSP because of `script-src 'self'` | low risk on this site, since there is no file upload and no JSONP              |
| Missing HSTS on `/cdn-cgi/content`        | internal Cloudflare endpoint returning `404`; I treated it as a false positive |
| `robots.txt` found                        | normal; the file does not expose sensitive paths                               |
| Technologies identified                   | informational; Astro/GitHub Pages/Cloudflare are expected                      |
| Missing `security.txt`                    | real; it needed fixing                                                         |

This stage was useful for one reason: it showed that not every alert deserves the same energy. Some were real fixes. Others were scanner noise. The work here was to classify before touching anything. And here came another long pause to study and understand how these alerts work.

## `security.txt`: when the file exists but production does not serve it

The first real problem was `security.txt`.

And what is this file for? Basically, it provides an official contact channel in case someone finds a vulnerability on the site. It is a convention standardized by RFC 9116. But what is that? Yes, I had no idea either. This standard was set by the IETF (Internet Engineering Task Force), the main open international organization responsible for developing and promoting the technical standards that make the Internet work. It defines protocols we use every day, such as HTTP (the web), TCP/IP (data transmission) and SMTP (email). The IETF published RFC 9116 in April 2022.

The goal was to create a quick, universal way for companies and websites to publish official security contact channels. That way, if an ethical hacker or security researcher finds a critical flaw on a company’s site, they know exactly where to send the report (preventing the flaw from being sold on the black market or exposed publicly before it is fixed).

With that cleared up, let’s move on!

In the repository, the file already existed at:

```text
public/.well-known/security.txt
```

But production responded:

```bash
curl -I https://www.marcopicanco.com/.well-known/security.txt
```

```text
HTTP/2 404
```

In other words: it was not enough for the file to exist in the project. What mattered was the public URL working.

To try to fix it, I added a `.nojekyll` inside `public/`, making sure the published output had:

```text
dist/.nojekyll
dist/.well-known/security.txt
```

Even so, to make the solution more explicit in Astro, I turned `security.txt` into an endpoint:

```ts
export function GET() {
  return new Response(
    [
      'Contact: https://www.linkedin.com/in/marcopicanco/',
      'Expires: 2027-07-23T00:00:00.000Z',
      'Canonical: https://www.marcopicanco.com/.well-known/security.txt',
      'Preferred-Languages: pt-BR, en',
      '',
    ].join('\n'),
    {
      headers: {
        'Content-Type': 'text/plain; charset=utf-8',
      },
    },
  )
}
```

The new file lives at:

```text
src/pages/.well-known/security.txt.ts
```

After the build, Astro started generating the route:

```text
/.well-known/security.txt
```

That was a small lesson about well-known files: `/.well-known/security.txt` is a public convention, but every host has its quirks. The scanner does not care whether the file is in the repo; it only checks whether the URL responds.

## HSTS: lagging alert vs. the real state

Cloudflare Security Insights still reported:

```text
Domains without HSTS
```

But production was already responding with:

```text
strict-transport-security: max-age=31556952
```

And HTTP was already redirecting to HTTPS:

```bash
curl -I http://www.marcopicanco.com
```

```text
HTTP/1.1 301 Moved Permanently
Location: https://www.marcopicanco.com/
```

Here I did not touch the code. The action was to validate and wait for the scanner to update. Not every dashboard reflects the current state right away, especially when DNS, CDN, cache and the edge are involved.

For now, I kept HSTS without `includeSubDomains` and without preload. That is on purpose. `includeSubDomains` can break subdomains that are not ready for HTTPS yet, and preload demands even more care because it puts the domain on a list that browsers consume.

## Port 8443: open, noisy and unnecessary

Another finding showed up in an external scanner:

```text
400 The plain HTTP request was sent to HTTPS port
http://www.marcopicanco.com:8443
```

This happens when someone tries to speak plain HTTP on a port that expects HTTPS. Port `8443` is a common alternative HTTPS port, and in my case Cloudflare itself was the one responding.

Even so, if I do not use that port, it does not need to be reachable. The fix was to block `8443` in Cloudflare.

The practical risk was not "someone breaking in through the 400 message". The risk was a larger surface and more noise:

- scanners discovering an alternative port;
- fingerprinting attempts;
- rules applied on `443` but forgotten on another port;
- possible confusion between HTTP and HTTPS;
- unnecessary alerts in reports.

Blocking what I do not use is a simple way to reduce the attack surface.

## DNS and the Dangling A Record alert

Cloudflare also reported:

```text
Dangling A Record detected
```

This deserves attention because dangling records can open the door to a takeover when DNS points to an abandoned resource. But in my case, the main records were the four official GitHub Pages A records:

```text
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153
```

And `www` pointed to:

```text
marcopicanco-dev.github.io
```

There was also this record:

```text
_domainconnect.marcopicanco.com
CNAME _domainconnect.domains.squarespace.com
```

Nothing suspicious there, because the domain was bought from and is managed by Squarespace. So this record makes sense for the registrar integration and should not be removed without a reason.

Result: I kept the records, treated the alert as a likely false positive and left it as something to keep an eye on. If an A record ever shows up pointing to a shut-down VPS, a deleted bucket or a service I no longer control, then it becomes an immediate action. For now, it stays.

## Bot Fight Mode and AI Labyrinth

Cloudflare recommended enabling Bot Fight Mode. For a static portfolio, that makes sense: there is no login, checkout, sensitive API or critical flow where an occasional challenge would have a big impact.

The recommended action is:

```text
Cloudflare Dashboard
Security
Bots or Security Settings
Bot Fight Mode
On
```

There was also a suggestion to review AI crawlers with AI Labyrinth. This feature sets traps for crawlers that do not respect crawling directives, especially when the goal is automated scraping. If you are not sure what a crawler is, don’t worry: it is also known as a `spider, bot or crawler`, an automated program that systematically sweeps the internet to analyze and index the content of web pages. And what is it used for in practice?

Search engines: Googlebot and Bingbot use crawlers to map the entire internet. Without them, search engines would not know which sites exist to show in their results.

For this site, I treat it as optional. If the goal is to reduce aggressive content scraping by AI crawlers, enabling it makes sense. If the priority is maximum predictability for crawling and SEO, it is worth testing calmly and watching the events in Cloudflare.

## A CI adjustment: when security turns into an unwarranted block

During this round, GitHub Actions started failing at this step:

```bash
npm run security
```

The reason was `npm audit` complaining about transitive vulnerabilities in ESLint-related development dependencies:

```text
brace-expansion
minimatch
eslint
eslint-plugin-jsx-a11y
```

These dependencies do not end up in the published static site. The public files are the HTML, CSS, JS and assets generated in `dist/`.

So I adjusted the script:

```json
"security:audit": "npm audit --audit-level=moderate --omit=dev"
```

This does not mean ignoring development dependencies forever. It means the deploy should not be blocked by a lint dependency that never reaches production. Updating ESLint and its plugins can be done separately, with a configuration migration if needed.

I also kept the post-deploy header validation as evidence, but without blocking the deploy when there is a temporary cache inconsistency:

```yaml
continue-on-error: true
```

This is a balance. I want to know when production does not look right, but I do not want to turn a cache-sensitive external check into deploy downtime.

## How I will approach the next vulnerabilities

Now that the initial foundation is better organized, I can move beyond headers and start exploring specific vulnerabilities methodically.

My roadmap for the next parts:

1. Validate whether the finding can be reproduced with `curl`, the browser or a simple script.
2. Find out whether the problem is in the code, the build, GitHub Pages, Cloudflare or the scanner.
3. Fix it at the smallest possible point.
4. Create a test or checklist so it does not regress.
5. Document before/after evidence.

Some topics worth exploring:

- the remaining CSP: reduce or remove `style-src-attr 'unsafe-inline'`;
- headers by file type: HTML, JS, CSS, images, 404 and Cloudflare endpoints;
- exposure of sensitive files;
- caching and how 404 pages behave;
- passive DAST scanners, such as OWASP ZAP;
- simple WAF rules for a static site;
- automating the CSP at the edge without copying hashes by hand;
- a future ESLint update to remove transitive dev vulnerabilities.

## Conclusion

Part 4 was less about "adding one more header" and more about operational maturity. Here I had to study more to understand which decisions to make and, above all, why.

The site was already much better than at the start, but the scanners showed what always happens in security: after the first fix, configuration details, false positives, CDN noise, fragile checks and decisions that need context start showing up.

The key point of this stage was to separate things out:

- real risk that needs fixing;
- a good but optional recommendation;
- a lagging alert;
- an acceptable false positive;
- a useful check that is too fragile to block a deploy.

With that, the initial phase is closed. From here on, I can explore specific vulnerabilities in more depth.
