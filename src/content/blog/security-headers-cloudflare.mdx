Depois de me deparar enxurrada de notícias sobre `cyber security`, resolvi testar meu site que por sinal é bem simples, é uma aplicação estática hospedada no github pages. Acabei de rodar um scanner de segurança e o resultado veio cheio de alertas: faltavam `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` e `Permissions-Policy`. Também apareceu um `Access-Control-Allow-Origin: *`.

Antes de sair adicionando headers, precisei entender uma limitação que muita gente esbarra ao hospedar em SSG estático: **o GitHub Pages não permite configurar headers HTTP customizados**. Não existe um `_headers` como na Netlify, nem controle de servidor. O quê o GitHub entrega, é o que o visitante recebe. E agora?

Isso dividiu o problema em duas partes:

## A primeira: O que dá pra resolver só no código?

Depois de algumas pesquisas vi que o `Content-Security-Policy` e o `Referrer-Policy` têm equivalente via `<meta>` no `<head>` do HTML, então dá pra aplicar direto no build do site.

Adicionei isso no layout raiz (`Base.astro`):

```html
<meta name="referrer" content="strict-origin-when-cross-origin" />
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'"
/>
```

Duas ressalvas importantes:

- CSP via `<meta>` **ignora a diretiva `frame-ancestors`**, que é justamente a que protege contra clickjacking. Só funciona como header HTTP real.
- O compilador do Astro renderiza o HTML injetando estilos, inline, enquanto seu runtime de hidratação injeta o `<style>` para interatividade. Sem servidor, não dá pra gerar um nonce por request, então precisei liberar `'unsafe-inline'` nos dois — senão a busca, o troca-tema e o menu mobile quebram.

Atualização depois da migração: na parte 3, essa decisão foi revisada. O `script-src 'unsafe-inline'` saiu e foi substituído por hashes gerados pelo Astro 7. A exceção que ficou é mais restrita: `style-src-attr 'unsafe-inline'`, usada pelos atributos `style=""` dos blocos de código.

Antes de finalizar, executei testes adicionais: gerei o build de produção, inspecionei as interações via protocolo CDP no Chrome Headless e monitorei o console durante fluxos críticos (busca, alternância de tema, menu mobile e navegação de posts). Na primeira rodada apareceu um bloqueio real: os posts do blog carregam fontes do Google Fonts via `@import`, e minha CSP inicial não liberava esse domínio. Como peguei esse tema free do Astro e fui fazendo costumizações, nem tinha me tocado desse pequeno detalhe, logo a ajustei `style-src` e `font-src` para incluir `fonts.googleapis.com`/`fonts.gstatic.com` e o erro sumiu. Mais tarde, eu perceberia que ia ter que atualizar o tema, mas esse assunto fica mais pra frente.

## A segunda: O que só dá pra resolver com um proxy na frente?

`X-Frame-Options`, `X-Content-Type-Options` e `Permissions-Policy` **só existem como header HTTP** — não há meta tag equivalente que os navegadores respeitem. Como o GitHub Pages não expõe isso, a solução foi colocar o domínio atrás do **Cloudflare** (plano free, é lógico!) e usar uma **Transform Rule → Response Header Transform Rule** pra injetar os headers na resposta antes dela chegar ao visitante:

| Header                         | Valor                                                          |
| ------------------------------ | -------------------------------------------------------------- |
| `X-Frame-Options`              | `SAMEORIGIN`                                                   |
| `X-Content-Type-Options`       | `nosniff`                                                      |
| `Permissions-Policy`           | `geolocation=(), microphone=(), camera=(), payment=(), usb=()` |
| `Access-Control-Allow-Origin`  | `https://www.marcopicanco.com`                                 |
| `Cross-Origin-Opener-Policy`   | `same-origin`                                                  |
| `Cross-Origin-Resource-Policy` | `same-origin`                                                  |

![Diagrama mostrando que CSP e Referrer-Policy são resolvidos via meta tag no HTML, enquanto X-Frame-Options, X-Content-Type-Options, Permissions-Policy e CORS só existem como header HTTP e por isso são resolvidos na borda, pelo Cloudflare](/images/security-headers-scope.svg)

Com o Cloudflare na frente, também aproveitei pra reforçar TLS: `Always Use HTTPS`, `Automatic HTTPS Rewrites` e HSTS. No caso do HSTS, fui com calma — antes de marcar `includeSubDomains` conferi via `dig`/`host` se existia algum subdomínio ainda sem HTTPS, porque isso é uma configuração **difícil de reverter** (o navegador guarda a política por meses) e o preload em `hstspreload.org` é praticamente uma via de mão única. Portanto, MUITO CUIDADO.

## A armadilha: não basta configurar o Cloudflare e achar que está protegido.

Aqui mora um detalhe muito importante. Depois de criar a Transform Rule com todos os headers, testei o site em produção pra confirmar — e os headers de resposta eram **idênticos aos do relatório original**: `server: GitHub.com`, `via: 1.1 varnish`, `x-fastly-request-id`, sem nenhum `cf-ray`, sem nenhum dos headers configurados. Nada tinha mudado, continuava a mesma coisa.

O motivo: eu tinha configurado a regra dentro da minha conta Cloudflare, mas o **domínio nunca foi delegado pro Cloudflare**. Os nameservers ainda eram os padrões do registrador (Google Domains, hoje Squarespace Domains), apontando direto pro GitHub Pages. Ou seja, o tráfego real dos visitantes nunca passava perto do Cloudflare — a regra existia, mas não tava servindo pra nada. Rodei:

```bash
dig +short NS marcopicanco.com
```

E confirmei: nameservers do Squarespace, não do Cloudflare. Zero efeito prático de tudo que eu tinha configurado até ali.

A correção foi trocar os nameservers no painel do registrador (Squarespace → **Servidores de nomes de domínio**) pelos dois que o Cloudflare atribuiu ao adicionar o domínio (algo como `xxxx.ns.cloudflare.com` e `yyyy.ns.cloudflare.com`). Depois de salvar, o Squarespace avisou que a mudança podia levar até 48h pra propagar — na prática, o `dig +short NS marcopicanco.com` já mostrava os nameservers novos em poucos minutos.

Mesmo com o DNS propagado, ainda teve mais uma etapa: tentar bater direto num IP do Cloudflare pra esse domínio devolvia erro de handshake TLS (`SSL routines::sslv3 alert handshake failure`). O Cloudflare detecta a troca de nameserver de forma periódica, não instantânea, e só depois disso emite o certificado SSL (Universal SSL) pro domínio — até esse certificado ficar pronto, a conexão HTTPS nem completa. Então, a sequência real de espera foi: propagação de DNS → detecção da zona pelo Cloudflare → emissão do certificado → só aí os headers passaram a valer.

![Diagrama comparando o fluxo de rede antes e depois: antes, o visitante ia direto pro GitHub Pages porque os nameservers ainda eram do registrador e o Cloudflare ficava fora do caminho; depois, com os nameservers apontando pro Cloudflare, o tráfego passa pela borda e recebe os headers de segurança antes de chegar ao GitHub Pages](/images/security-dns-before-after.svg)

A lição: **depois de configurar qualquer proteção de borda (Cloudflare, WAF, CDN), sempre valide direto na URL de produção** — headers configurados num painel não valem nada até o tráfego de fato passar por ali. Uma regra "pronta" que nunca é aplicada é pior do que não ter regra nenhuma.

## Fechando outras pontas

Como o site é pessoal, estou usando pra efeito didático e logo fiz uma varredura leve e não-destrutiva nele mesmo: tentei bater em `.git/config`, `.env`, `package.json`, `astro.config.mjs` e outros arquivos comumente esquecidos expostos — todos 404, como esperado (só o `dist/` é publicado). Certificado TLS válido, TLS 1.2/1.3 respondendo normalmente.

Duas coisas que não existiam e são boa prática de qualquer site, sem relação direta com o relatório original:

- **`robots.txt`**: Corrigida a falha de rota (404) no ambiente do GitHub Pages através da inclusão do arquivo, configurado para liberar a indexação global do site.
- **`security.txt`** ([RFC 9116](https://www.rfc-editor.org/rfc/rfc9116)): é o arquivo padrão (`/.well-known/security.txt`) pra alguém que encontrar uma vulnerabilidade saber como reportar, sem precisar caçar meu contato em algum lugar. Coloquei apontando pro meu LinkedIn.

## Dependências e automação

Rodei `npm audit` e apareceram vulnerabilidades em pacotes transitivos do Astro (rollup, sharp, prismjs, yaml). Tentei `npm audit fix` — e ele resolveu "corrigindo" isso pulando o Astro de v4 pra v7 de uma vez, o que quebrou o build (`ViewTransitions` não existe mais na API nova). Revertido na hora. Upgrade de maior versão não é fix de segurança, é migração, e vou fazer isso com calma, em outro momento, testando cada parte. (Sim, ela será feita, na pate 2 desse artigo).

O que fica automatizado pra não esquecer disso de novo: um `.github/dependabot.yml` com checagem semanal de `npm` e `github-actions`, mais os alertas de segurança do Dependabot ativados no repositório — assim, na próxima vulnerabilidade, chega um aviso (ou um PR) em vez de descobrir só quando rodar o scanner de novo.

## Resumo

| Item                              | Onde foi resolvido                  |
| --------------------------------- | ----------------------------------- |
| Content-Security-Policy           | `<meta>` no HTML                    |
| Referrer-Policy                   | `<meta>` no HTML                    |
| X-Frame-Options                   | Cloudflare (Transform Rule)         |
| X-Content-Type-Options            | Cloudflare (Transform Rule)         |
| Permissions-Policy                | Cloudflare (Transform Rule)         |
| Access-Control-Allow-Origin solto | Cloudflare (Transform Rule)         |
| HSTS                              | Cloudflare (Edge Certificates)      |
| Delegação de DNS pro Cloudflare   | Nameservers trocados no registrador |
| robots.txt / security.txt         | Arquivos novos em `public/`         |

Site estático no GitHub Pages é ótimo pelo custo zero e pela simplicidade, mas vale saber onde termina o que o código resolve sozinho e onde começa o que precisa de uma camada de rede na frente — e, mais importante, **testar direto na URL de produção** antes de dar por resolvido. 🔒
